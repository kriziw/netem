What {{ branding.name }} is for

{{ branding.name }} is a transparent WAN impairment appliance for resilience, failover and SD-WAN testing. It sits inline between a firewall/router and one or more upstream networks, then applies controlled network conditions with Linux tc/netem. The appliance is vendor-neutral: it changes the path itself and lets the device under test react using its own SLA probes, routing logic and failover policy.

Core idea: configure the topology once, define what each WAN represents, then operate the lab from Overview, WAN Links and Scenarios while Analytics shows the effect.

Recommended first-use sequence

  1. Open Settings → Topology & interfaces and map the inner/outer interface pair for each WAN.
  2. Leave Restore WAN bridges on startup enabled unless you intentionally want an ephemeral topology.
  3. Leave Restore selected WAN profiles and quality enabled for an appliance-like deployment.
  4. Open Settings → Access profiles and verify that the DIA/DSL/Broadband/4G/5G/Satellite baselines are suitable for the lab.
  5. Open WAN Links, choose the access profile and nominal line rate for each WAN, then apply the configuration.
  6. Open Overview and confirm both paths are visible, expected SLA state is sensible and live traffic counters move when traffic crosses the firewall.
  7. Run a low-risk test such as Progressive brownout from Scenarios.
  8. Observe how the SD-WAN/firewall reacts, then use Analytics to compare traffic with the condition NetEm injected.

A safe first test

Use the Progressive brownout scenario against the backup WAN first. It gradually moves through quality levels rather than immediately dropping traffic. This helps confirm that the topology, impairment engine, live state and scenario restoration all behave as expected.

Scenarios → Progressive brownout → select target WAN → Run → watch Overview / Analytics → wait for automatic restore

Persistent configuration vs runtime actions

NetEm deliberately distinguishes between saved WAN configuration and transient test actions. Access profile, nominal bandwidth, quality mode and custom impairment values are persisted in config.json. Runtime blackholes and temporary MTU constraints are test conditions and are not intended to replace the saved profile.

Scenarios temporarily change runtime state while running. When a scenario finishes or is stopped, the configured WAN profile is restored. This lets you repeatedly run a test without manually rebuilding the baseline afterward.

What “Live” means

Throughput and packet-rate values are calculated from Linux interface counters. Latency, jitter, loss and quality shown by NetEm are the values being injected by the impairment engine, not active measurements of a remote target. The generic SLA evaluator therefore represents the state NetEm expects from the injected conditions. Future vendor adapters can add the appliance's observed SLA values beside that expected state.

How to return the lab to normal

For a manual WAN fault, use WAN Links → Restore. For a running scenario, use Stop & restore WAN. For a temporary MTU test, choose Restore original. If you have manually changed the saved quality/profile, move the quality slider back to the desired level and apply the WAN configuration.

Recommended operating habit: always establish a known 100% baseline before starting a scenario. This makes failover timing and SLA behavior easier to interpret.
