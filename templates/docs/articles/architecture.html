Transparent inline topology

Each emulated WAN is a transparent Layer-2 path. NetEm does not need an IP address on the WAN bridge or WAN-facing ports. Only the management interface needs normal IP connectivity for the web interface, SSH and updates.

SD-WAN / firewall │ inner NIC │ br-wanX │ outer NIC │ upstream / ISP router

The bridge forwards Ethernet frames between the two physical/virtual interfaces while Linux traffic control applies impairments to egress traffic on those ports.

Direction mapping

The directional telemetry model follows the physical datapath, not interface naming conventions:

  • Download: bytes/packets transmitted on the inner interface toward the firewall.
  • Upload: bytes/packets transmitted on the outer interface toward the upstream router.

The REST telemetry endpoint also retains all raw RX/TX counters for diagnostics.

Where impairments are applied

The normal profile applies latency, jitter, loss and advanced packet behavior on the inner interface. Upload bandwidth is separately rate-limited on the outer interface so asymmetric circuits can be modeled. The UI presents this as one WAN even though Linux applies controls at specific egress points.

Interpretation: the latency value is an injected one-way impairment on the configured path. A ping through the path may observe roughly that additional delay as part of round-trip behavior depending on where the probe originates and returns.

Bridge persistence

Linux bridges and qdiscs are runtime objects; they disappear across reboot unless recreated. NetEm stores topology and profile settings in config.json and can recreate the bridges and saved shaping when the service starts.

These settings are controlled under Settings → Topology & interfaces:

  • Restore WAN bridges on application startup — recreates the transparent bridges and reattaches inner/outer interfaces.
  • Restore selected WAN profiles and quality — reapplies the persisted profile/qdisc after startup.

Why management is separate

The management interface is intentionally excluded from WAN interface selection. This prevents a test that blackholes, rate-limits or reconfigures a WAN from cutting off the NetEm web UI itself. In a virtual lab, place the management NIC on a dedicated management bridge/VLAN and use separate virtual NICs for every WAN datapath.

Linux traffic-control model

NetEm uses Linux tc with the netem qdisc for delay, jitter, packet loss, correlation, duplication, corruption and reordering. Bandwidth limiting is applied with TBF. The Diagnostics tab shows the raw qdisc output so you can verify what the kernel accepted.

NetEm clears the current root qdisc before applying a new profile. This keeps each Apply operation deterministic rather than incrementally stacking old settings.

Carrier state vs data-plane failure

Blackhole faults intentionally preserve Ethernet carrier. That matters for SD-WAN testing: the appliance cannot simply react to “interface down”; it must detect that the data plane or health-check path has failed. One-way blackholes let you test asymmetrical failures that are harder for SLA logic to diagnose correctly.
