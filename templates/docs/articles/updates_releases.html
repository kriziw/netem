One place for every update

Settings → Updates installs and checks the three components of a lab from one page:

  • NetEm, the operator interface, tests and showroom, from the stable release on origin/main. NetEm restarts itself after an install.
  • Traffic Simulator, the simulated users, installed from its own release. The simulator restarts after an install. Tests and workloads block installs while they run.
  • Controlled target, the target on the ISP router, updated over its management connection. Connect or change that connection under Settings → Agent & target.

Each card shows what is installed and the latest release. Keep the NetEm and simulator versions matching when you can; the Updates page warns when the simulator and target differ.

Stable update channel

The in-app updater always compares the installed checkout with origin/main. It does this regardless of the local branch name. This prevents older installations from becoming stranded when an old feature branch is merged and deleted.

Check stable channel

Check stable channel performs a Git fetch of origin main, refreshes the remote version and recalculates ahead/behind state.

Install update

An update is available only when origin/main has a newer release than the installed version. Merged commits that are not yet released do not count. Updates are fast-forward only. The updater refuses to install when:

  • tracked application files are modified;
  • the installation has commits that are not part of the release;
  • the stable remote branch cannot be found;
  • Git fetch/merge fails.

On success, NetEm fast-forwards to the release commit (git merge --ff-only <release commit>), then exits intentionally. A correctly configured systemd unit with Restart=on-failure starts the updated application again.

While this happens, a progress screen steps through Installing update, Restarting NetEm and Reconnecting, then reloads the page on the new version. It knows the restart has finished when a new NetEm process answers, so it also works when an update does not change the version number. If the update is refused, for example because of local changes, the screen says why and nothing restarts. If NetEm takes more than two minutes to come back, it suggests checking journalctl -u netem -n 50 on the appliance.

Repository ownership

The configured service account must be able to write the repository when the in-app updater fetches and fast-forwards. Running manual Git commands as a different account can create objects under .git/objects that block the service user. Examples use the netem service and /opt/netem directory from the README; substitute the configured names on an existing appliance.

Preferred manual Git pattern:

NETEM_USER=$(systemctl show netem -p User --value)
NETEM_USER=${NETEM_USER:-root}
runuser -u "$NETEM_USER" -- git -C /opt/netem status
runuser -u "$NETEM_USER" -- git -C /opt/netem fetch --prune origin

If ownership has already become inconsistent:

systemctl stop netem
chown -R "$NETEM_USER" /opt/netem
runuser -u "$NETEM_USER" -- git -C /opt/netem status
runuser -u "$NETEM_USER" -- git -C /opt/netem fetch --prune origin
systemctl start netem
Design principle: system administration can be done as root, but repository/application-file operations should be performed as the service owner.

Release Please

The repository uses Release Please to manage semantic versions and release changelog PRs. The version source is version.txt; release configuration lives in release-please-config.json and .release-please-manifest.json.

Commit conventionTypical release effect
fix:Patch release
feat:Minor release
Breaking changeMajor release
docs:, chore:, etc.Included in changelog policy as configured; does not normally imply a feature bump by itself

After qualifying changes reach main, Release Please prepares/updates a release PR. Merging that release PR updates the version/changelog and creates the corresponding tag/GitHub release.

Testing an unmerged feature branch

The in-app updater intentionally follows main, so it will not install an unmerged feature branch. For a one-time preview, stop the service and switch branches manually as the configured service account, then restart the service. Return to main when testing is complete.
