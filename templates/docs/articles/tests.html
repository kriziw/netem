Guided tests and conditional orchestration

The Tests page groups capabilities by validation outcome instead of implementation primitive. A test can now combine timed impairment stages with state-driven wait and assert stages.

Built-in tests

Progressive brownout, SLA failover, Flaky underlay and Availability stress remain available as one-click tests. The built-in SLA failover test includes two assertions: expected SLA must fail after the blackhole and recover after the path is restored.

Phases and length

Every built-in and site test runs about 3–5 minutes in named phases, for example Baseline → Degradation → Severe brownout → Recovery. That is long enough for SD-WAN health checks to react and for the 60-second experience window to show the effect, and short enough to repeat. Each test card shows its planned length and phases.

Change Length before starting to stretch or shrink a test (1–60 minutes). Delays between stages and DEM measurement windows scale with it; timeouts on conditions do not, so a check still gets the time it needs.

Announced before it starts

Every test, including each test of a site test plan, is announced for 5 seconds before it changes anything. The showroom shows what is coming: the test, its WAN, what each phase does and what is checked. The running-test bar counts down meanwhile. Stop & restore during the announcement cancels the test without touching the WAN; pausing becomes available once the test runs. The test's clock and its report start when the announcement ends.

Pause a phase

Pause phase in the running-test bar on the Command Center or Tests page holds the test in its current phase, with its impairment still applied, until you select Resume. Use it to explain what is happening or to let a slow appliance react. Paused time does not count toward the test's length, and the showroom marks the test as paused. Stop & restore still ends the test at any time.

Supported scenario actions

ActionPurpose
qualityApply a 0–100% access-model quality level.
faultApply/clear bidirectional or one-way blackholes.
mtuApply 576–9000 byte MTU, or 0 to restore.
waitPause until a condition becomes true or the timeout expires.
assertEvaluate a condition as a pass/fail requirement; result is written to the Lab Session report.

Condition sources

  • Expected SLA: wait/assert on pass or fail for the scenario WAN or an explicitly named WAN.
  • Active probe: compare probe success or latency_ms using == != < <= > >=.
  • Measured traffic: compare persisted down_mbps, up_mbps, down_pps or up_pps.

Conditional stages support 1–600 second timeouts, 0.25–5 second polling, and on_fail behavior of stop or continue. A failed condition marks the overall scenario failed even when execution continues.

Conditional example

[
  {"after":0, "action":"quality", "value":100, "label":"Baseline"},
  {"after":10, "action":"fault", "value":"blackhole", "label":"Inject outage"},
  {"after":0, "action":"assert",
   "condition":{"type":"sla","state":"fail"},
   "timeout":5, "label":"Expected SLA detects failure"},
  {"after":20, "action":"fault", "value":"normal", "label":"Restore path"},
  {"after":0, "action":"wait",
   "condition":{"type":"sla","state":"pass"},
   "timeout":10, "label":"Wait for recovery"}
]

Probe assertion example

{"after":0, "action":"assert",
 "condition":{
   "type":"probe",
   "probe_id":"probe-wan1-internet",
   "field":"success",
   "op":"==",
   "value":false
 },
 "timeout":8,
 "label":"Internet probe fails"}

Probe conditions reject stale results instead of treating an old success/failure as current evidence.

Traffic path readiness

Simulated users only measure the WANs when their traffic reaches the controlled target through the appliance. The Command Center and the Tests page show the traffic path the Traffic Simulator reports:

  • its data interface is up with its address;
  • its route to the target goes through the selected appliance;
  • the target answers.

Before NetEm starts a workload, either from the Corporate traffic controls or in a test, it checks this path:

  • If the simulator can put the path right, NetEm asks it to and waits. The simulator brings the data interface back with its saved address and restores the selected appliance route.
  • If the path still is not ready, NetEm refuses to start and says why. For example, with no appliance selected, the traffic would leave through the simulator's management interface and bypass the appliance and NetEm.

Repair traffic path does the same on demand. Older simulators are checked through their selected route and repaired by selecting it again.

While a test runs, two findings flag measurements that cannot be trusted:

  • The test's workload is not running on the Traffic Simulator: the simulator restarted, or NetEm is connected to a different simulator.
  • Simulated traffic is not crossing NetEm: transactions complete, but no WAN carries them.

Running-test state

The running-test bar shows the test, its WAN, the current phase and stage, any condition it is waiting for with the latest observed value, the phase timeline, the elapsed time against the planned length and when the next phase starts. Stop & restore interrupts both timed waits and conditional polling.

Test summary

When a test ends, NetEm summarizes it: the result and checks passed, a short conclusion, and per phase the experience score, request success (with its lowest point), interactive P95, average traffic per WAN and the SD-WAN steering verdict per traffic class. SD-WAN remediation lists which traffic the appliance moved off which WAN, how fast, and whether that met the active site's steering target. The latest summary appears on the Tests page and on the showroom; summaries of tests run in a lab session are part of its report. Summaries need the Traffic Simulator to measure user experience.

Assertions and Lab Sessions

Start a Lab Session before running a scored validation. Every assertion writes an assertion event containing the requirement, observed value, elapsed evaluation time and PASS/FAIL result. Completed session reports aggregate those results automatically.

Security and capture tools

EICAR, benign beacon and bounded packet capture remain on the same Tests page. These are diagnostics/detection-validation tools and are not used as unrestricted offensive functionality.
