What a Lab Session is

A session is the evidence container for one validation objective. Tests describe the impairment; the session records what happened, what was measured and whether explicit assertions passed.

Start a session

  1. Open Sessions.
  2. Name the objective, for example the customer and site.
  3. Choose the client site: industry, sub-industry, site function, size and criticality. The active site profile is preselected.
  4. Start the session.
  5. Operate normally from Command Center, Tests and Analytics.
  6. Complete the session when the validation is finished.

Starting a session also makes its site the active site profile, so experience targets, the Command Center badge and the showroom all describe the same client.

The active session ID is attached to runtime events, SQLite WAN telemetry and active-probe samples.

Completed session report

Completing a session generates and persists a report snapshot. The report includes:

  • overall result: PASS, FAIL or UNSCORED, and the client site;
  • a summary of each test: conclusion, per-phase experience, success, response time, WAN traffic and steering, and SD-WAN remediation;
  • scenario runs and their completion status;
  • every conditional assertion and observed value;
  • WAN telemetry statistics such as peak throughput, worst injected latency/loss, minimum quality and expected-SLA-fail sample count;
  • active-probe sample count, success rate, average/P95/max response time;
  • event-category summary and an evidence timeline.

The HTML report can be printed/saved as PDF by the browser and has a JSON export route for automation.

How PASS/FAIL is determined

If any assertion fails or a scenario ends in failed, the report result is FAIL. If at least one assertion ran and all assertions/tests passed, the result is PASS. A session with no assertions is UNSCORED rather than being incorrectly labelled successful.

Storage

Up to 100 session records are kept in runtime/sessions.json. WAN/probe samples live in runtime/telemetry.db. The report snapshot itself is stored with the completed session record so the evidence summary does not change later when retention windows roll forward.

Service restart behavior

An in-progress session is marked interrupted after process restart rather than being silently resumed. This avoids claiming continuity when scenario/probe runtime context may have been lost.

Still planned

Capture-file attachment, vendor-observed SD-WAN events and side-by-side session comparison are still future capabilities. The reporting and assertion model is already structured to receive them.
