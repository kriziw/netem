What a Lab Session is

A session is a named container for a validation objective. Tests describe the impairment you run; the session describes why you are running it. Example: FortiGate SD-WAN failover validation.

Start a session

  1. Open Sessions.
  2. Enter a short objective-oriented name.
  3. Click Start session.
  4. Operate the lab normally from Command Center, Tests and Analytics.

The active session appears in the global top bar. Newly written runtime events automatically receive the session ID.

What is associated

Any event created through the common runtime logger while the session is active is tagged. This includes scenario stages, manual quality changes from the Command Center, faults, MTU actions, bandwidth quick changes, packet capture activity and safe security-test events.

Complete a session

Click Complete session when the validation run is finished. This records the end time and writes a final session event. Completing a session does not itself alter WAN state, so restore/finish any active test first if you want a clean end state.

Session history

The appliance retains up to 100 session records in runtime/sessions.json. The history currently shows name, ID, start time, duration and the number of retained events associated with the session.

Event-count scope: the event log itself retains up to 500 events, so very old session event counts can decrease after older events roll out of retention.

Service restart behavior

Active sessions are intentionally not resumed after an application restart because the in-memory test context may no longer be reliable. A session that was active when the process stops is marked interrupted when history is loaded again.

What Sessions enable next

The current implementation establishes identity, timing and event correlation. It is intentionally the foundation for richer evidence later: baseline snapshots, individual test results, attached PCAPs, vendor-observed SLA/path changes, pass/fail assertions and downloadable HTML/PDF reports.
