Troubleshooting method

Separate problems into four layers: application, Linux topology, impairment/qdisc, and traffic itself. Verify one layer at a time instead of changing multiple settings simultaneously.

Web/UI problem? ↓ Flask/service status ↓ correct bridge/interface mapping ↓ tc/qdisc state ↓ Linux interface counters ↓ firewall/SD-WAN behavior

Live throughput stays at 0

  1. Confirm traffic is actually using the selected WAN on the firewall.
  2. Open /api/v1/telemetry and note traffic.download.bytes and traffic.upload.bytes.
  3. Refresh after a few seconds while generating traffic. The relevant counters should increase.
  4. If they do not, compare the raw inner/outer counters and verify topology mapping.

On the VM, inspect counters directly:

ip -s link show enp6s19
ip -s link show enp6s20
ip -s link show enp6s21
ip -s link show enp6s22

If Linux counters increase but the UI does not, check browser developer tools for failed requests to /api/v1/telemetry or /api/v1/state.

Latency/loss works but bandwidth limiting does not

Open WAN Links → Adjust link → Diagnostics and inspect the raw qdisc output on inner and outer interfaces. NetEm expects the relevant netem/TBF qdiscs to be accepted by the kernel.

tc -s qdisc show dev enp6s19
tc -s qdisc show dev enp6s20
tc -s qdisc show dev enp6s21
tc -s qdisc show dev enp6s22

If the UI reports an Apply error or TBF is missing, preserve the exact command/error output before changing the topology. This differentiates a UI/state issue from a kernel traffic-control hierarchy issue.

WAN traffic stops after reboot

Check Settings → Topology & interfaces and confirm startup bridge restore is enabled. Then inspect:

ip link show br-wan1
ip link show br-wan2
bridge link

If the bridges are absent, check the service log for startup errors.

Service will not start

systemctl status techkarma-netem --no-pager
journalctl -u techkarma-netem -n 100 --no-pager

Also validate Python imports from the repository:

cd /opt/techkarma-netem
./.venv/bin/python -m py_compile app.py netem_core.py
./.venv/bin/python -c 'from app import app; print(app.url_map)'

Update fails with “insufficient permission for adding an object”

This normally means Git objects were created by a different user, commonly root. Normalize ownership and test Git as the service user:

systemctl stop techkarma-netem
chown -R techkarma:techkarma /opt/techkarma-netem
runuser -u techkarma -- git -C /opt/techkarma-netem status
runuser -u techkarma -- git -C /opt/techkarma-netem fetch --prune origin
systemctl start techkarma-netem

Avoid plain root-owned Git operations in this checkout afterward.

Packet capture does not start

Check both the executable and service capabilities:

command -v tcpdump
systemctl show techkarma-netem -p User -p AmbientCapabilities -p CapabilityBoundingSet

tcpdump should be present and the service should have CAP_NET_RAW. Shaping itself normally needs CAP_NET_ADMIN.

Scenario appears stuck

Check the Scenarios active banner and the event timeline. Each after value is a wait before the next action, so a long interval may be intentional. Use Stop & restore WAN to request termination. If the service was interrupted mid-test, reapply the normal saved profile from WAN Links.

Expected SLA result looks wrong

Remember that the generic SLA evaluates NetEm's injected values, not the firewall's measured probe. Verify the SLA thresholds in Analytics and the current effective delay/jitter/loss in /api/v1/state. Any active blackhole makes the data-plane check fail.
